# Interactive VLM Feedback Loop - Overview

*Labeling with ICL; Optional Fine-Tuning*

**Version 1.0.0**

---

## 1. Executive Summary

### The Problem

Most vision machine learning projects slow down not because models can’t perform, but because **obtaining high-quality labels and iterating on behavior** is expensive and slow. Domain experts can spot errors immediately, but the typical loop (label → wait → retrain → redeploy) can take multiple weeks.

### The Interactive Loop

First, a **Subject Matter Expert (SME)** defines the **Guidance** (the task description, label schema, and rules that tell the model what to label and how) and ingests a batch of **Unlabeled** images. This blueprint then collapses the iteration cycle into an interactive workflow where:

1. The selected Teacher **Vision Language Model (VLM)** proposes a label for an image.
2. The **SME** reviews the proposal and chooses one action:
  - **Accept** if correct
  - **Edit** if wrong
  - **Skip** to omit the image
  - **Retry** to re-run the proposal after changing the model and/or the Guidance

   The image viewer supports zoom and pan controls for closer inspection.
3. Accepted/edited examples become **Verified** ground truth immediately.
4. Verified Edits are eligible to influence subsequent model calls via **in-context learning (ICL)**.
5. **Repeat** until proposals are consistently accepted (edits become rare).

### Data Readiness + Efficient SME Ordering

To reduce wasted SME effort, the blueprint includes an ingestion and scheduling layer:

- **CLIP-style image embeddings are computed automatically** in the background at ingest via the **NVIDIA NeMo Retriever VL 1B v2 embedding NIM** (Spec §5.5). Embeddings optimize the order in which images are presented to SMEs, increasing diversity and breadth early while avoiding near-duplicates and monotony.

### From Labeling to Scale-Up

The Interactive Loop gets you high-quality **Verified** labels quickly, and helps you converge on a trusted **Teacher + Guidance + ICL** setup. While you label, the system continuously measures quality; tracking evaluation accuracy, Accept rate, and Test Pool coverage. The **Scale-Up Readiness Gate** determines when the trusted Teacher setup may begin Batch Labeling. Student Training is a separate path: server-side start validation verifies TAO, training data, and the selected Student bases when the SME starts it.

- **Batch labeling:** After the gate passes, run the Teacher over large volumes of Unlabeled images to generate **Auto-Labeled** fully synthetic labels without per-image human review.
- **Fine-tune a Student:** Open Student Training independently of the Batch Labeling gate. Export datasets and use **Cosmos-RL / TAO VLM fine-tuning** (NVIDIA TAO Toolkit) to fine-tune one or more Student models to support lower latency and higher concurrency, then export and deploy behind **NIM** and compare accuracy/latency results.

*Future direction:* deploying the Teacher + ICL setup directly (without fine-tuning) was removed in v1.0 — a static export cannot reproduce the loop's per-query ICL example selection — but a runtime-ICL deployment service may return in a future release.

### Minimal Setup

The Teacher is served behind an **NVIDIA NIM** OpenAI-compatible endpoint. A minimal Interactive Labeling setup needs only a **build.nvidia.com API key**. The system pre-fills the hosted NIM endpoint URL, seeds a model catalog with defaults, and computes embeddings automatically. Self-hosted NIM is also supported.

## 2. Key Concepts

Core terms for the Interactive Labeling workflow, evaluation, and data management. Additional concepts for Batch Labeling and Student Training are introduced in §5.

**Guidance** - Task definition: Description, Schema, and Rules. Description/Rules are versioned (each Guidance record is an immutable version).

**SchemaCore** - Stable label contract: field identities, names, types, roles (**Core/Aux**), allowed values, validation constraints. **Core fields** are required and define evaluation correctness. **Aux fields** are optional, never affect evaluation or proposal validity, and are generated by the model before Core fields to often serve as observational scaffolding (Spec §4.4). A small set of Core edits (rename, exact enum value rename, presentation metadata) are allowed in place; all other Core changes trigger Re-verification (Spec §4.4).

**Unlabeled** - An ingested image not yet reviewed/labeled by a human.

**Omitted** - An image excluded from the workflow.

**ICL** - In-Context Learning: showing the model a small set of relevant examples alongside the query image.

**Verified** - An image+label pair confirmed by a human (ground truth). Verified examples not tagged for the Test Pool are eligible to influence subsequent model calls via **in-context learning (ICL)** (Edits only; see Spec §6.2).

**Teacher** - Model served via NVIDIA NIM used to propose labels. During interactive review, proposals confirmed by SMEs become Verified ground truth. Also used in Batch Labeling (§5).

**Model catalog** - A configured list of model entries for the project. Each entry declares its **eligible roles** (`teacher`, `student_base`), which determine where it can be used. See Engineering Specification §4.8 for seeded defaults.

**Rationale note** - An opt-in auxiliary explanation of visible evidence, controlled by a toggle in Guidance and disabled by default. When enabled, the Teacher requests it last and the SME reviews it after editing a label. When disabled, the model is not asked for it and the SME never enters a rationale-correction flow. It never affects Core validity or evaluation and is excluded from production Teacher ICL. The toggle follows the ordinary Aux-field edit rule, so it can change freely without invalidating labels (Spec §4.4, §6.3.2).

Toggling does not backfill or erase historical labels. If a project enables,
disables, and later re-enables the feature, its corpus may contain a mix of
examples with and without notes; this is an accepted tradeoff for avoiding
mandatory SME explanation work.

**Test Pool** - A reserved subset of Verified examples used for evaluation and excluded from ICL. Pool management is automatic: the system assigns examples to the Test Pool based on a configured fraction and CLIP-embedding diversity.

**Exact Match (Core Fields)** - Deterministic routine comparing model output to the Verified label on **Core fields** only, after schema-defined normalization.

**Retry (UI action)** - User requests a new proposal attempt for the same image after changing the Teacher model (from the catalog) and/or the Guidance, to see whether the proposal improves. Retry creates a new model invocation and returns the user to Save / Skip / Retry again.

**CLIP embedding** - A vector representation of an image computed automatically at ingest by NVIDIA NeMo Retriever VL 1B v2 (hosted with the same API key as Teacher, or the system-managed local NIM). "CLIP" names the contrastive image-text embedding class, not the retired legacy Blueprint NV-CLIP path. Used by the review selector to present semantically diverse images. See Spec §5.5 for provider options and consistency rules.

**pHash (perceptual hash)** - A compact image fingerprint computed inline at ingest (CPU-only). Baseline diversity signal for the review selector before CLIP embeddings are available. See Spec §5.6.

**Generation Controls** - Two user-facing toggles that govern model invocation behavior: **Output Stability** (Precise [default] / Explore, mapping to `temperature`/`top_p`) and **Thinking** (ON [default] / OFF per model, controlling reasoning). See Spec §6.7.

**Visual Budget Controls** - Capability-gated, model-aware presets (**Fast** / **Balanced** / **High Detail**) that manage how images are preprocessed before model inference, controlling per-image visual token spend via model-specific `mm_processor_kwargs`. The default is **High Detail**, favoring higher image fidelity because resolution is the dominant perception lever for perception-bound fields. Only exposed when the active Teacher supports visual token controls. See Spec §6.9.

The Labeling header persists the selected Teacher and all three generation
controls as one next-proposal contract. A change does not re-run the proposal
already on screen; after the setting finishes saving, the next proposal
(whether reached through Save, Skip, or Retry) uses the new value.

**Action Request** - A pre-filled, read-only message generated by the system when the SME is blocked by an infrastructure dependency they cannot resolve themselves. Contains the technical requirements and current diagnostic context. The SME copies it to clipboard and pastes into any communication tool. See Spec §10.3.

## 3. Interactive Labeling: The Interactive Loop

### Step 1: Ingest Images and Create Guidance (SME)

The SME first ingests **images** to be worked through in the review loop (ingestion persists a storage reference plus source metadata). At ingest the system **computes a pHash for each image inline** (CPU-only, immediate) and **begins computing CLIP embeddings in the background** via the configured embedding provider (Spec §5.5).

While embeddings compute, the SME defines the **Guidance**:

- **Description:** what the model should do.
- **Schema:** the JSON label fields (types, allowed values, and roles **Core/Aux**).
- **Rules:** edge cases and policy text.

Labeling may begin immediately using pHash-diverse selection; the review selector upgrades to CLIP-diverse mode as embeddings become available.

### Step 2: Select the Next Image for Review (system)

The system maintains a labeling review selector over all examples that are not yet **Verified** or **Omitted**.

To choose the next item to present, the system uses the best available diversity signal:

- **CLIP-diverse mode** (preferred):
When CLIP embeddings are available, the system selects the next item using those embeddings to maximize semantic diversity.
- **pHash-diverse mode** (baseline):
When CLIP embeddings are not yet available, the system selects the next item using pHash hamming distance to maximize perceptual diversity. pHash is always available because it is computed inline at ingest.

### Step 3: Propose a Label via Teacher + ICL (system)

For the selected Unlabeled image, the system deterministically:

- selects a small set of eligible Verified examples (ICL). Only SME-corrected **Edits** are eligible (they carry the corrective signal; Accepts add none). By default the set is chosen for **query relevance** — the Edits whose CLIP embeddings are nearest the image being labeled (newest-first fallback before embeddings are ready). Token/image budgets prune the least relevant tail, then the two strongest retained matches bookend the rendered list (rank 1 first, rank 2 last).
- renders a compact production prompt with the real field schema and Core-only ICL labels. It deliberately omits verbose Guidance Description/Rules prose while Guidance remains the versioned source of schema and task provenance,
- calls the selected Teacher model via NVIDIA NIM to produce a JSON label and, only when enabled in Guidance, a rationale note.

For the selected Auto-Labeled image, the system surfaces the existing Auto-Labeled label (from Batch Labeling) as the editable proposal. No new Teacher call is made — the SME reviews what Batch Labeling produced. The SME can still Retry to get a fresh Teacher proposal if the Auto-Labeled result is unsatisfactory.

If the project is at cold start (no Verified yet), ICL selection yields zero examples, and the system still proceeds with inference.

Where supported (as determined by a runtime capability probe), the system uses structured generation (JSON schema derived from SchemaCore). If structured generation is unavailable, prompt-only generation receives the same compact, prompt-visible field contract; it never refers to a schema that was not rendered. Deterministic validation/scoring remains in the backend.

### Step 4: Review (SME)

For each proposed label, the SME reviews the proposal in an editable form and takes one of three actions:

- **Save:** stores the label as Verified. If the SME modified any fields, the system records `verified_outcome=Edit`; if unmodified, `verified_outcome=Accept`. When rationale notes are enabled, an Edit also requires rationale review. When disabled, Save has no rationale step.
- **Skip:** no label recorded → example is omitted and will not be presented again. If the proposal came from Batch Labeling, its machine label is discarded; restoring the image later returns it as clean Unlabeled work.
- **Retry:** change Teacher model (from catalog) and/or Guidance, then re-run proposal → returns to the same review.

A **Reset** action is available when the SME has modified any field; it restores all fields to the VLM's original proposal.

### Step 5: Immediate Eligibility (system)

Once an example becomes Verified via Edit, it becomes eligible for ICL selection on subsequent calls (subject to token budget limits and pool exclusions). Accepted examples are not selected for ICL; only Edits carry corrective signal.

## 4. Evaluation

During Interactive Labeling, the system evaluates by re-running the current Teacher+Guidance+ICL setup against a held-out Test Pool to check that accuracy has not degraded as new images are introduced and Guidance is refined. The system recommends evaluations at key moments (first pool threshold, configuration changes, ICL growth); the SME decides when to run them. Evaluations always run in the background.

The Test Pool is a **reserved subset of Verified** used for evaluation, excluded from ICL selection. Pool management is fully automatic: the system assigns Verified examples (both Accepts and Edits) based on a configured fraction and CLIP-embedding diversity. No user action is required (see Engineering Specification §4.3). Reviewing images in CLIP-diverse order — the default review selector behavior — interleaves classes as you label, which keeps the Test Pool and the ICL (non-pool) set class-representative so evaluation metrics reflect true accuracy across all classes.

**Returning vs New metrics.** Because the Test Pool grows over time, a naive overall accuracy number can be misleading: accuracy may drop not because the model degraded, but because a hard example joined the pool. To separate these signals, each evaluation reports metrics in two buckets:

- **Returning**: examples that were in the previous evaluation's snapshot. This is the regression signal. Did accuracy hold or degrade on the same set of images?
- **New**: examples added to the pool since the last evaluation. How does the model handle the latest images?
- **Overall**: the combined number across all pool members.

The primary display places the previous Overall accuracy next to the current Returning accuracy on the same images. This side-by-side comparison directly answers "did we get better or worse?" New and Overall are secondary context. See Engineering Specification §7.1.2 for the reporting contract.

As the Test Pool grows, evaluations take longer. The system runs evaluation inferences concurrently (provider-aware and configurable: 1 at a time against hosted endpoints for rate-limit politeness, 8 against self-hosted/local NIMs) and always in the background. The SME is never blocked.

The evaluation pipeline also applies to **Student** variants (after fine-tuning, to compare tradeoffs and gate releases).

## 5. Batch Labeling and Student Training (Optional)

### 5.1 Key Concepts for Batch Labeling and Student Training

**Scale-Up Readiness Gate** - System-evaluated, configurable gate that determines whether the Teacher+Guidance+ICL setup meets quality criteria for Batch Labeling. The system automatically evaluates evaluation metrics, Accept rate, and Test Pool size against configurable thresholds and presents a plain-language verdict. See §7 and Engineering Specification §7.3.

**Auto-Labeled** - A model-generated label produced by Batch Labeling without SME validation. Not ground truth; used for training scale.

**Batch Labeling run** - A long-running job that applies the Teacher with ICL to many Unlabeled images and stores Auto-Labeled outputs with lineage and filtering metadata.

**Student** - Optional model(s) fine-tuned via Cosmos-RL / TAO VLM, then served via NIM. Trainable base models limited to catalog entries with the `student_base` role (currently Cosmos Reason2 8B/2B and Cosmos 3 Nano/Super reasoner). Multiple Student variants may be trained and compared.

**Student variant** - A deployed Student endpoint characterized by either a selected **NIM model profile** or a **custom quantized checkpoint** loaded through `NIM_MODEL_NAME`.  Different variants are treated as distinct for evaluation and latency comparisons (see Engineering Spec §2.3).

### 5.2 Batch Labeling (Teacher-run fully synthetic label generation)

**What it is:**
Batch Labeling runs the **Teacher** over a large Unlabeled corpus to generate **Auto-Labeled** fully synthetic labels without per-image SME review.

**When to do it:**

When the **Scale-Up Readiness Gate** passes and the SME explicitly approves. The system automatically evaluates configurable thresholds and presents a plain-language readiness verdict:

- Evaluation quality: overall Exact Match and per-core-field match rates
- Accept rate over recent labels
- Minimum Test Pool size

The SME does not interpret raw metrics; the system says "Ready" or "Not yet, here's why." See §7 for the gate UI.

**Why it exists:**
To generate far more labeled data than a human can feasibly review one-by-one-specifically to create a much larger training set for a Student model.

Auto-Labeled outputs are **not** ground truth. Verified remains the source of truth for evaluation and governance.

### 5.3 Student Training: Fine-tuning Student Model(s) (Optional)

If enabled:

1. The system exports versioned training artifacts (Verified excluding Test Pool, plus optional Auto-Labeled) with manifests and checksums. The Test Pool is exported separately as a Verified-only TAO evaluation dataset; Auto-Labeled predictions are never used as its answer key.
2. The system triggers a **Cosmos-RL / TAO VLM** supervised fine-tuning job (external execution) and persists lineage from exports → TAO job → registered Student.
3. When training succeeds, the system automatically runs a **TAO evaluate** job against the Test Pool export to establish baseline quality. Default quantization (**FP8_DYNAMIC**) is then applied, followed by another TAO evaluate on the quantized checkpoint. This chain runs without SME intervention.
4. TAO per-sample predictions are re-scored by the system's canonical
   Core-field evaluator (Appendix A.2) over the complete frozen Test Pool
   export. The archive must still match its recorded checksum and contain one
   ground-truth row and one prediction per frozen sample; missing, duplicate,
   corrupt, or replaced evidence fails quality validation instead of changing
   the accuracy denominator or selecting by artifact order.
5. Students are deployed behind NIM for serving validation (latency, throughput). The system attempts local NIM orchestration via Docker; if local deployment is not possible, an Action Request provides the deployment details for external infrastructure.

### 5.4 Multi-Student Training and Comparison

The first-run validation workflow produces two variants for one recommended
small base: a full-precision baseline and `FP8_DYNAMIC`. It uses the Quick
preset and expands to four jobs (train, baseline evaluate, quantize, FP8
evaluate). Multiple bases and additional quantization schemes are available
only through the explicit production-candidate comparison workflow.

Quality comparison (from TAO evaluation, always available after training):

- Accuracy metrics (Appendix A.2): overall Exact Match rate, per-core-field match rate, per-value precision/recall/F1 for categorical Core fields

Serving comparison (from NIM evaluation, available after deployment):

- Latency metrics (p50/p90/p99 end-to-end latency; time to first token (TTFT) / inter-token latency (ITL) when available) per configured concurrency
- NIM profile metadata (backend, precision, TP, optimization target)

### 5.5 Student NIM Hosting and Quantization

Students are **hosted behind NVIDIA NIM** using the **vLLM backend**. The seeded models carrying the `student_base` role are **Cosmos Reason2 8B/2B** and the **Cosmos 3 Nano/Super reasoner**.

Each precision/profile variant is a distinct Student variant. Variants may differ in optimization target (latency vs throughput), tensor parallelism, and precision. All metadata is recorded so accuracy/latency comparisons are reproducible. To compare variants, register each as a distinct entry in the model catalog and run the same evaluation against the Test Pool (see Appendix E).

Quantization uses the TAO Cosmos-RL `quantize` action; see Engineering Specification §9.8 for details and constraints.

## 6. Onboarding / First time user experience (Interactive Labeling Quickstart)

The onboarding / first-time user experience should be optimized around one goal: **get the user to their first Verified labels quickly** (Interactive Labeling), with the fewest possible decisions and minimal UI friction.

### Recommended first-run flow (UI)

1. **Create (or select) a Project**

   Prompt for a Project name. The system creates a project directory under the workspace root (see Engineering Specification §1.7) to hold the project database and generated artifacts. Images are not copied; the system records paths to their original locations.

2. **Configure NIM endpoints**

   The system probes the environment at startup (Engineering Specification §1.5 Mode C, environment assessment) and presents a **recommended per-service configuration** for Teacher inference and embeddings. Teacher and embeddings are configured independently — the system recommends the best mode for each based on available credentials and hardware.

   **Auto-configure (skip) when fully configured:** if enough credentials and capabilities are detected to configure both services without user input, skip this step entirely and proceed to step 3 with a non-blocking banner showing the auto-selected configuration (e.g., *”Teacher: hosted NIM. Embeddings: deploying locally.”*). A healthy exact Blueprint-managed Teacher resident is auto-reused when it matches the current quality recommendation: project creation attaches its endpoint, selects its matching model configuration, and skips the deploy/key choice even when `NVIDIA_API_KEY` is also configured. A different resident remains an explicit keep/replace decision.

   **Show recommendation screen when decisions are needed:** the system presents two rows (Teacher, Embeddings), each showing the recommended mode and a **[Configure]** override. Only missing credentials are prompted inline, labeled with why each is needed. Recommendation logic is quality-first, then hardware-gated: Omni on supported ≥80 GB / compute-capability ≥9.0 GPUs; CR3-Nano on ≥56 GB when Omni is ineligible; Cosmos Reason2 2B on 36–55 GB. Super and Cosmos Reason2 8B remain selectable. With an API key and no preferred resident, a fitting local Teacher is recommended for faster response times. Labeling starts immediately on the hosted default while the local NIM downloads, then the project switches atomically to local after health, served-model, and inference verification pass. Hosted-only remains available. A 10–35 GB GPU runs the local NeMo Retriever VL embedding NIM with a hosted Teacher; below 10 GB, embeddings are hosted or pHash.

   **Path-aware Screen 2A (FTU Phase I + NIM-FTU-Local-Peer):** when a GPU is detected, the single-purpose key-paste page renders one of three layouts based on the recommendation:
   - **Resident reuse — recommended Teacher already running:** project creation has already attached and selected it, so Screen 2A queues no Teacher deploy. It auto-skips when embeddings are already usable (the normal single-GPU case); if another GPU is free and local embeddings are recommended, setup continues only for that embedding NIM. No Teacher model reload is needed.
   - **Case A — no key + GPU + local Teacher fits:** primary card invites running the named recommended Teacher locally with [Deploy locally →]; a peer card below offers the hosted default Teacher (MiniMax-M3) via an inline API-key paste.
   - **Case B — key set + GPU + local Teacher fits (hosted bridge):** the primary card recommends the named local Teacher for faster responses. The SME starts labeling immediately with the configured hosted default while the local NIM downloads in the background; after verification succeeds, the backend switches the project to local atomically. A peer card keeps **Hosted only** available for SMEs who do not want a download or GPU change.
   - **Case C — no key + no GPU:** today's hosted CTA, unchanged. Case D (key + no GPU) auto-skips.

   When the SME accepts a local path (Case A or Case B local recommendation), the FTUE Screen 2C confirm fires `POST /v1/projects/{id}/local_nim/deploy` per queued model (Teacher first, embedding second) in the background — paralleling how the embedding NIM has always deployed. Case B includes `activate_on_success=true`, so the hosted Teacher remains usable during download and the backend activates local only after health, served-model, and inference verification. Exact healthy Teacher reuse normally happened earlier, atomically with fresh-project creation; the deploy endpoint retains the same reuse check for later model changes and races. If a different Blueprint-managed NIM occupies the needed GPU, setup identifies the current model/project and asks the SME to **Keep current NIM** or **Stop current & start the requested NIM**. It never stops the resident on the first click. The labeling screen renders a non-blocking banner via `LocalDeployBanner` while a new container is in `starting`.

   - **NVIDIA API Key** field: shown when hosted NIM is part of the recommendation and the key is not yet configured. **”Get NVIDIA API Key”** links to `https://build.nvidia.com/settings/api-keys`. Test connection via `GET /v1/models`.
   - **NGC API Key** field: shown when local deployment is part of the recommendation and the key is not yet configured. **”Get NGC API Key”** links to `https://org.ngc.nvidia.com/setup/api-key`. Helper text: *”Required for pulling NIM container images.”*
   - **[Configure]** per service: opens inline override to switch between hosted NIM, self-hosted URL, or deploy locally. Self-hosted URL entry covers any remote NIM (LAN, cloud). If no endpoint is available, a **”Request NIM Setup”** Action Request (Spec §10.3) provides the handoff.
   - **Post-onboarding local model changes:** NIM Configuration lists every Blueprint-supported Teacher compatible with the currently detected GPU, marks the quality recommendation and running resident, and deploys only the model the SME selects. The first deploy request is always non-destructive. If every compatible GPU is occupied, the screen names the exact resident model, GPU, and owning project and requires **Keep current** or **Replace NIM** confirmation. A confirmed replacement activates the new Teacher only after health, served-model, and inference verification pass; a failed replacement best-effort restores the displaced resident.
   - **Missing prerequisites screen:** when local deployment is recommended but Docker or NVIDIA Container Toolkit is missing, the system shows copy-ready install commands and a reference to the `setup-local.sh` prerequisite script (Engineering Specification §1.8.1). The SME (or admin) runs the script, then restarts the application.
   - Local embedding NIM deployment starts in the background on confirmation, paralleling how CLIP-style embeddings compute in the background after ingestion. NeMo Retriever VL NIM 2.0.0 uses a 10 GB eligibility floor, so 10–35 GB single-GPU hosts take the embedding-only path automatically.
   - **Single-GPU + local Teacher (Engineering Spec §1.5 one-NIM-per-GPU invariant, F49 amendment 2026-05-19; empirical motivation re-confirmed on Cosmos 3 nano / H100 NVL, 2026-07-13):** on a host with exactly one GPU, the FTUE deploys the Teacher only; image embedding falls back to pHash diversity (Spec §5.6) and CLIP-diverse review selection is unavailable until the SME either adds a second GPU or configures an `NVIDIA_API_KEY` for hosted embeddings. Student NIM benchmarking on a single-GPU host displaces the resident Teacher for the duration of the benchmark and best-effort auto-restores it afterward (Engineering Spec §9.5.2 steps 0 and 9).

3. **Confirm seeded defaults (fast-path by default)**

   **Skip** when the selected Teacher is valid and its endpoint is connected. The selection is the exact reused local Teacher when one was adopted during project creation; otherwise it is the effective hosted default (`minimaxai/minimax-m3` by default). Proceed directly to step 4 with a non-blocking banner naming the actual selection.

   **Show confirm screen** when the default is missing, invalid, or the user connected a custom endpoint where seeded models may not exist. Preselect the effective `DEFAULT_TEACHER_MODEL` (`minimaxai/minimax-m3` by default, read from `EnvironmentResponse.default_teacher_model_name`) as the Teacher.

4. **Ingest images (before Guidance; gives CLIP time to compute)**

   The SME selects images via an in-app file/folder browser that navigates the **backend host's** filesystem (Engineering Specification §10.2.10). A path field above the tree accepts an absolute directory path: pressing Enter (or clicking a Recent path chip) navigates the tree to that location, so power users can paste a known path and skip the click-through. The SME then checks individual image files and/or whole directories in the tree and clicks **Ingest Selected**. Checking a directory recursively ingests every supported image beneath it.

   **Important:** The file browser shows the filesystem of the machine running the backend, not the machine running the web browser. If the backend runs on a remote server, the browser navigates that server's directories. This is by design: images are stored by reference (not copied), so they must be on a filesystem the backend can access.

   Accepts JPEG, PNG, WebP, BMP, and single-page TIFF; animated GIFs and multi-page TIFFs are rejected. The SME can add additional folders at any time; ingestion is cumulative, not one-shot.

   - During ingestion, show a progress indicator with running counts: images accepted, images skipped (unsupported format or duplicate `example_key`), and errors. Partial success is acceptable: successfully ingested images become `state=”Unlabeled”` immediately; failures are reported inline without blocking the rest of the batch.
   - pHash is computed inline during ingestion (no wait). CLIP embeddings compute in the background while the SME creates Guidance (step 5), so most are ready by the time labeling starts.
   - After ingestion completes, show a summary: total Unlabeled count, any skipped/failed items.
   - **Low image count notice:** if fewer than 150 images were ingested, show a non-blocking warning: *“We recommend at least 150 images so the default 40% allocation can fill the 60-image Test Pool. All 150 must become Verified to meet that mathematical minimum; model-quality needs may be higher.”* **[Add more images]** · **[Continue]**. This is a recommendation, not a gate. The bundled 15-image sample receives additional copy identifying it as a walkthrough that cannot pass the default Scale-Up gate.

5. **Create Guidance**

   The SME builds the blueprint that tells the model what to do. A **”Start from:” dropdown** (Blank, Classification, Multi-label, Attribute extraction, Damage severity, Recycling classification, Coarse grocery classification) appears at the top of the screen. It defaults to Blank. Selecting a template pre-fills Description and proposes a starter schema so the SME has something to react to instead of starting from nothing. Once the SME edits anything, the dropdown has no further effect.

   Below the template selector, three cards appear in the order the SME thinks about the task:

   - **Description** (*”Describe the task and what the model should focus on in each image.”*). The schema defines the output structure; this tells the model the domain and what to pay attention to. Can be empty.
   - **SchemaCore** has two sections:
     - **Core fields** (*”These are the critical answers. They are evaluated. Unlike other fields, changing Core fields after labeling starts means re-labeling your existing images.”*).
     - **Aux fields** (*”Optional fields. You may use them to make the model describe what it sees before it decides.”*). Can be empty. A dedicated **Rationale notes** toggle lives here and defaults off; it can be enabled or disabled later without invalidating labels.
   - **Rules** (*”Optional. How should the model handle ambiguous or tricky images? Edge cases tend to surface during labeling, so you can always add Rules later.”*). Can be empty.

   Sticky footer carries Cancel and Save. Errors block save. See Engineering Spec §6.6 for the full UI contract.

6. **Start labeling (immediate Interactive Labeling loop)**

   On entering the labeling view, immediately request a proposal for the first Unlabeled image. Show a loading state while the Teacher generates the proposal.

   - **Cold start notice:** on the first proposal (Verified = 0, no ICL examples), show a one-time dismissable hint: *”This is your first label. The model has no examples to learn from yet. Accuracy improves immediately with every Edit.”*
   - Present the image and proposal side-by-side in an editable form with three actions: **Save / Skip / Retry**. If the proposal is correct, Save stores it as-is (one-click). If the SME modifies a field, a **Reset** action appears. The rationale panel and its Save gate appear only when rationale notes are enabled; the default disabled workflow saves the corrected fields directly.
   - The top bar shows the active Teacher model and controls (Output Stability, Thinking, Visual Budget). All defaults are pre-set; no action required from the user.
   - If the proposal fails (schema-invalid, timeout, endpoint error), surface the failure inline and offer **Save** (manual label) and **Retry** without leaving the screen.
   - After Save, the system immediately advances to the next image and requests a new proposal. Saved labels where the SME modified fields (`verified_outcome=Edit`) become eligible for ICL on subsequent calls.
   - **Schema refinement reminders:** two dismissable hints nudge the SME to review their schema before re-labeling becomes expensive. The first fires at 10 Verified labels (*”Need to adjust your schema? Fewer labels to re-do now.”*), the second at 35 (*”You have {N} labels. Schema changes mean more images to re-label.”*). Each fires at most once per project. See Engineering Spec §6.8 for the trigger contract.
   - See §6 “Labeling screen considerations” for detailed UX guidance and Engineering Spec §6.3 for the full inference and review contract.

### Labeling screen considerations (UI)

- **Keep the user in flow:**
  - The image, proposal, and actions should be visible without navigation to other pages.
  - Save should be a one-click action when the proposal is correct (no modifications needed).
- **Minimize cognitive load for first-time users:**
  - Provide an editable form with **Core fields** (required) first, then **Aux fields** (optional, visually secondary). Core fields are the SME's primary task: they define correctness. Aux fields are visible but secondary.
  - **When rationale notes are disabled (default):** omit the field from prompting and proposals, show no rationale text or panel, and impose no rationale work on the SME. Saving an Edit requires only the corrected label fields.
  - **When rationale notes are enabled:** request the field last and hide it until the SME engages with the label. The UI MUST NOT show a produced rationale alongside the proposal because this prevents model prose from anchoring the SME’s judgment. The rationale is revealed only after the SME begins modifying a field:
    - On **Accept:** the rationale is not shown. The SME confirms the label is correct without seeing the model’s reasoning. The Teacher’s rationale is retained silently.
    - On **Edit:** after the SME selects Edit (or begins changing a field value), the rationale panel expands below the label fields with a clear requirement: *”Update the rationale to match your corrected label.”* The SME MUST address the rationale before the Save button is enabled. Two paths:
      - **Write it directly:** edit the rationale text. The panel shows **”Edited”** state. Save is enabled.
      - **Have the AI rewrite it:** click **Generate AI Rationale** → the system calls the Teacher with the image and active task context, withholding both the original proposal and the SME's correction so the writer must inspect independently → the SME waits (inline loading state) → the regenerated rationale is displayed → the SME reviews and either edits the result (Save enabled) or clicks **Approve AI Rationale** (Save enabled). The writer describes the subject the active task asks about and separates a carrier from displayed content only when that distinction matters.
    - Save is blocked (disabled with helper text: *”Review the rationale before saving”*) until the rationale is in an approved state: either Edited or AI-regenerated-and-approved. Whitespace-only changes do not count as meaningful edits.
    - The review workflow retains rationale as audit context. It is not fed back into production Teacher ICL and never determines label correctness.
- **Fast recovery from failures:**
  - If a proposal is schema-invalid / timeout / endpoint error, surface the failure inline and offer **Edit** (manual label), **Retry**, or **Skip**.
- **Missing image files:**
  - If the image file is not found or unreadable when the labeling screen tries to display it, show a broken-image placeholder with a message (e.g., *"Image not found at original location."*) and offer **Skip**. Do not crash or block the labeling session.
- **Retry should feel lightweight:**
  - Retry is a small inline interaction that lets the user change any combination of Teacher model, Guidance version, Output Stability, Thinking, or Visual Budget, then re-run the proposal without leaving the labeling screen.
- **Generation Controls (Spec §6.7):**
  - Show **Output Stability** (Precise / Explore) and **Thinking** (ON / OFF) in the top bar next to the Teacher model selector.
  - Thinking toggle is shown only after the endpoint capability probe confirms support. Unknown or unsupported models use their natural reasoning default and receive no toggle override.
- **Visual Budget Controls (Spec §6.9):**
  - Show **Visual Budget** (Fast / Balanced / High Detail) in the top bar alongside Generation Controls.
  - Hidden when the active Teacher does not support visual token controls (Spec §6.9).
- **Adding more images:**
  - An **Add Images** action is always available from the labeling screen (same file browser / path entry as onboarding step 4). Newly ingested images enter as Unlabeled and appear in the review selector immediately. No interruption to the current labeling session.
- **Schema refinement reminders:**
  - Two reminders nudge early schema review: at 10 Verified labels (fewer labels to re-label) and at 35 (last call before re-labeling becomes expensive). Each fires at most once per project. Frame positively: adjusting the schema is easier now than later. See Spec §6.8.
- **Evaluation:**
  - The system reserves a fraction of Verified examples into a **Test Pool** (Engineering Spec §4.3). Show a persistent Test Pool counter on the labeling screen once the pool has members (e.g., "Test Pool: 7 images").
  - **First evaluation recommendation:** when the Test Pool reaches 5 images, an inline banner recommends the first evaluation: *"{N} images reserved for testing. Run an evaluation to measure quality."* **[Evaluate]** **[Dismiss]**. The banner's [Evaluate] runs an evaluation directly so the SME doesn't need to track down the strip button. While a schema refinement reminder is on screen (see "Schema refinement reminders" above), this banner is suppressed so the SME sees one nudge at a time.
  - After the first evaluation completes, show a persistent summary line. On subsequent evaluations, the summary places the previous accuracy next to the current accuracy on the same images: `Previous: 82% (15) → Same images now: 85% (15) · New: 60% (5 new)`. This side-by-side comparison is the core signal: did we get better or worse on images we have already tested? The summary updates automatically as evaluations re-run.
  - **Configuration change nudge:** whenever the SME changes Guidance, Teacher model, Generation Controls, or Visual Budget, an inline banner recommends an evaluation: *"Settings changed since last evaluation. Run an evaluation to check accuracy with current settings."* **[Dismiss]**
  - **ICL growth nudge:** when the number of Edits has doubled since the last evaluation, an inline banner recommends an evaluation: *"{N} new edits since last evaluation. Run an evaluation to see if accuracy improved."* **[Dismiss]**
  - Manual evaluation is always available. An **Auto-Evaluate** toggle (OFF by default) skips the banners and runs evaluations automatically on each trigger.
  - Evaluation metrics and Accept rate feed the Scale-Up Readiness Gate (§7). The labeling screen shows a non-blocking gate progress indicator so the SME can track readiness naturally during labeling.
## 7. Onboarding / First time user experience (Scale-Up Quickstart: Batch Labeling + Student Training)

This second-stage onboarding is **optional** and is available after the user has begun the Interactive Loop. The **Scale-Up Readiness Gate** governs Batch Labeling only; Student Training remains navigable and applies its own server-side TAO/data checks on submission. The goal is to help a first-time user safely scale from high-quality Verified labels to (a) large volumes of **Auto-Labeled** data and (b) one or more deployable **Student** models.


### How infrastructure dependencies are handled

Scale-Up workflows introduce dependencies (TAO endpoints for training, GPU-equipped compute, NIM endpoints for Student deployment) that are infrastructure tasks, not labeling tasks. The SME is never expected to provision or configure these.

When the system detects that the SME is blocked by an infrastructure dependency, it generates an **Action Request**: a pre-filled, read-only message containing the exact technical requirements and current diagnostic context that the SME cannot be expected to know or transcribe. The SME clicks **Copy to Clipboard** and pastes into Slack, email, or whatever channel their organization uses.

Two Action Request types surface inline on the screen where the blocker occurs, not in a settings page:

- **Request NIM Setup**: self-hosted NIM endpoint needed (onboarding step 2)
- **Request TAO Setup**: TAO endpoint not configured or unreachable

Deployment handoff is an Action Request type (`deployment_handoff`) with richer content (checkpoint reference, NIM configuration, evaluation summary, training lineage), but the interaction is the same: read-only formatted content with Copy to Clipboard.

Action Requests are not a ticketing system. The system produces a message; where it goes is the organization's choice. See Engineering Specification §10.3 for the full contract.

### Recommended first-run flow

#### 1) Enter a dedicated "Scale Up" hub (gate-first landing)

When the user clicks **Scale Up** (or completes enough Interactive Labeling), land them on a single page that answers: "Am I ready to batch label?", "Am I ready to train a Student?", and "What happens next?"

**Scale-Up Readiness Gate (Batch Labeling)**

The system automatically evaluates readiness for Batch Labeling against configurable thresholds and presents results in plain language. The SME does not interpret raw metrics; the system says "Ready" or "Not yet, here's why."

Gate criteria (all must pass for system readiness; all thresholds are configurable per project):

- **Evaluation quality:** Latest evaluation overall Exact Match meets the configured threshold (default: 80%). Every Core field individually meets the per-core-field match rate threshold (default: 80%). Every value of every categorical Core field (enum, enum set, boolean) meets the minimum per-value F1 threshold (default: 80%). If no evaluation has completed, this criterion fails with: *"Run an evaluation to measure quality."*
- **Accept rate:** Rolling Accept rate over the most recent N verified labels (default: 80% over last 50) meets the configured threshold.
- **Minimum Test Pool size:** The Test Pool contains at least the configured minimum number of members (default: 60). Below this, the sample is too small for reliable evaluation.

Gate UI presentation:

- When all system criteria pass: [Run Batch Labeling] is enabled. Clicking it IS the SME's confirmation to proceed.
- When any system criterion fails: [Run Batch Labeling] is disabled. The system shows the most important next step(s) in plain language with a [Details] button for the full criterion breakdown.

**Readiness cards (informational context alongside the gate):**

- **Teacher readiness**
  - Active Teacher model config shown (from catalog).
  - Active Guidance shown (with version).
  - Gate criteria status: Accept rate (with rolling window details), latest evaluation results (with per-criterion pass/fail).
- **Data readiness**
  - Counts: Verified, Unlabeled, Auto-Labeled, Omitted.
  - Pool status: Test Pool size (with minimum pool size criterion status).
- **Capability readiness**
  - Batch Labeling availability (feature flag / deployment capability).
  - Student Training readiness comes from the backend training preflight,
    including TAO reachability and timeout support, workspace, credentials,
    selected Student-base roles, and usable data. The card shows checking,
    ready, data-not-ready, or infrastructure-required. The last state includes
    a **Request TAO setup** Action Request (Spec §10.3).

**Primary CTAs (only two):**

- **Run Batch Labeling** (gated): disabled until Scale-Up Readiness Gate passes (all system criteria met). Clicking it when enabled IS the SME's confirmation. When disabled, shows the reason (first failing criterion). Thresholds are configurable if the SME needs to adjust the bar.
- **Train a Student** (always enabled as navigation; the destination screen explains and enforces TAO/data blockers on **Start Training**)

If the gate has not passed, show a banner:

> "The Scale-Up Readiness Gate has not passed. Continue Interactive Labeling to improve quality metrics. **[Go to Labeling]**"

#### 2) Batch Labeling quickstart (Teacher-run synthetic labels)

The Teacher, Guidance, ICL, and images are already configured from Interactive Labeling. Batch Labeling is a single screen. New images can be added at any time from the labeling screen (see "Adding more images" in §6).

The screen shows the active Teacher, Guidance version, ICL edit count, Visual Budget preset, and input count so the SME can verify the configuration before running. A **Run Batch Labeling** button launches the run.

> **Teacher:** `<active Teacher model>` · **Guidance:** `<active Guidance version>` · **ICL:** `N` edits · **Visual Budget:** `<active preset>` (shown only when Teacher supports it) · **Input:** All Unlabeled (excluding Omitted)

Optional filters (collapsed "Advanced"): ingestion date range. Core-invalid outputs are discarded; valid outputs (including Aux fields) are stored and exported.

> "Batch Labeling generates **Auto-Labeled** outputs. These are **not** ground truth until reviewed."

**Run status page** (supports "walk away and come back"):

- Progress: processed / total.
- Live schema-valid Core rate vs schema-invalid Core rate, with common error types and a downloadable manifest of schema-invalid examples.
- A single **Export dataset** CTA when the run completes.

#### 3) Student Training quickstart (Cosmos-RL / TAO VLM)

Student Training should feel like "review the validation plan, confirm its
cost, then start" rather than "configure TAO." After explicit confirmation,
the system handles training, quality evaluation, quantization, and quantized
evaluation with no further SME interaction until results are ready.

**Screen layout:**

The screen shows all training configuration in one view with sensible defaults pre-selected. The user reviews, optionally adjusts, and clicks **Start Training**.

**Student base models (top section)**

**Validate training setup** selects one recommended small Student base
(preferring Cosmos Reason2 2B), rather than every catalog entry. A seeded entry
whose TAO experiment is missing remains selectable and is provisioned in the
Training Jobs monitor. **Compare candidate variants** is the explicit
advanced workflow for selecting multiple bases.

**Training intensity (single dropdown)**

- **Quick** (validation default): fast iteration, fewest epochs
- **Standard**: recommended production-candidate baseline
- **High Quality**: more epochs for better accuracy
- **Max Quality**: large-epoch train for best quality (slowest)

Raw hyperparameters are hidden by default. An "Advanced" expander shows the resolved patch JSON read-only (Spec §9.7.3.1).

**Training data sources**

- **Verified (train):** always included (Verified excluding Test Pool). Not deselectable.
- **Auto-Labeled:** included by default from the completed Batch Labeling run. The user can deselect to train on Verified only.

The backend-authoritative summary separates Verified Training Pool, held-out
Test Pool, eligible Auto-Labeled, excluded examples and reasons, and the final
usable training total. Start remains disabled when that usable total is zero.

**Quantization**

Checkboxes for which quantization schemes to evaluate after training. Each selected scheme produces a quantized variant for comparison alongside the full-precision baseline.

- **FP8_DYNAMIC** (selected by default): broadly compatible, modest quality trade-off.
- W4A16, W8A8, W8A16: additional schemes, not selected by default.

Deselecting all schemes means: train + evaluate baseline only, skip quantization.

**Server-side start validation**

The configuration screen continuously runs the authoritative backend
preflight and renders each check. The backend also repeats the same validation
when the SME submits. It fails closed before launching work unless:

- The TAO endpoint is reachable (Eng Spec §1.6).
- TAO accepts the configured safe stale-job timeout.
- The recorded TAO workspace is bootstrapped and reachable.
- Each selected base model has the `student_base` role.
- At least one Verified training example remains after excluding the Test Pool.

A selected base whose TAO experiment is missing is not an error. Its
provisioning appears as the first Training Jobs step. If every selected base
is ready, that step is not displayed.

Before submission, a mandatory confirmation dialog shows the selected bases,
resolved preset, generated variants, exact expanded job count, usable training
and Test Pool counts, and a warning that the remote workflow is long-running.
Usable data below 150 is explicitly described as wiring validation rather than
production-quality model evidence.

**Start Training button**

On click, the system:

1. Creates the Training Jobs record and navigates to its monitor.
2. If needed, provisions all selected missing bases together under **Provision Student Bases**. This step is omitted for an already-ready selection.
3. Creates versioned dataset export artifacts (manifests, checksums, DatasetExport records per Spec §13.5) from the selected data sources. Exports the Test Pool as a separate Cosmos-RL evaluation dataset.
4. For each selected base model, creates and chains TAO jobs automatically:
   - **Train** (TAOJob, `action: "train"`)
   - **Evaluate baseline** (TAOJob, `action: "evaluate"`, against Test Pool export)
   - **Quantize** per selected scheme (TAOJob, `action: "quantize"`)
   - **Evaluate quantized** per scheme (TAOJob, `action: "evaluate"`)
5. Jobs within each model's chain run sequentially. Chains for different models also run sequentially (one model at a time).

The Training Jobs monitor remains the project entry point while this work is
active. **Cancel Jobs** asks for confirmation, then best-effort cancels every
remaining setup and TAO job while preserving completed work. The project is
released from Training Jobs immediately after local cancellation; if TAO does
not confirm a remote cancellation, the monitor warns that the remote work may
still be running. The canceled state offers **Back to Projects** as its exit.

On completion of all chains: CTA **Compare Students** (proceeds to Compare & Deploy).

#### 4) Evaluate and deploy (closing the loop)

After all TAO chains complete, the **Compare & Benchmark** view shows quality
results immediately—no NIM deployment is required for the initial comparison.
The Teacher is the accuracy baseline. This screen validates quality and
temporary serving behavior and prepares a production handoff; the Blueprint
does not own the permanent production service.

**Phase 1: Quality comparison (TAO-backed, available immediately)**

TAO evaluation results are re-scored by the system's canonical Core-field evaluator (Appendix A.2). Results are presented as side-by-side cards per Student variant (baseline + quantized), with the Teacher as the accuracy baseline:

- Accuracy metrics: overall Exact Match rate, per-core-field match rate, per-value precision/recall/F1 for categorical Core fields.
- A metric selector and optional chart let the SME drill into per-value breakdowns and visually compare variants.

The SME can use quality results alone to make directional decisions: discard underperforming variants, identify which are worth benchmarking on NIM.

**Phase 2: Serving Benchmark (NIM-backed, user-scoped)**

TAO provides the quality comparison; NIM provides the serving performance characterization. The NIM phase is a targeted **Serving Benchmark** whose primary outputs are latency and concurrency behavior across configured load levels, not a second quality gate.

The SME selects which variants to benchmark rather than benchmarking all automatically. Scope options: **Benchmark all**, **Benchmark selected** (checkbox per variant card), or **Benchmark this variant** (per-card action). This avoids wasting time benchmarking variants that are already poor on TAO-backed quality. Selected variants run sequentially (one container at a time, GPU resources shared). Results are shown **progressively** as each variant completes — the SME does not wait for all benchmarks to finish.

For each selected variant, the system orchestrates the NIM lifecycle:

- **[Benchmark]** — when the NIM deployment preflight passes (Docker, NVIDIA Container Toolkit, GPU memory, NGC API key available on the backend host). The system orchestrates: start → health poll → evaluate → benchmark across configured concurrencies → stop. Each variant is bounded by per-variant timeouts (startup: `NIM_STARTUP_TIMEOUT_S`, default 1200s; benchmark: `NIM_BENCHMARK_TIMEOUT_S`, default 1200s). On timeout or failure, the variant is marked accordingly and the queue continues with the next selected variant.
- **[Deploy for serving validation]** — when the preflight fails. The system
  generates a `student_nim_deploy` Action Request with the exact `docker run`
  command, checkpoint path, NIM release, GPU requirements, and environment
  variables pre-filled. The SME hands this to infrastructure, registers the
  temporary endpoint, and runs the serving benchmark. This label is distinct
  from **Request production deployment**.

After a variant's benchmark completes, its card immediately shows: latency p50/p90/p99 (client boundary), TTFT/ITL when available, request throughput/RPS across concurrency levels, and NIM profile metadata.

No global workflow timeout is required in v1. Per-variant timeouts independently bound each benchmark. Failed or timed-out variants do not invalidate completed results.

**Deployment handoff:**

Each Student variant card with both quality and serving validation has a
**Request production deployment** button that generates a
`deployment_handoff` Action Request (Eng Spec §10.3). It contains checkpoint
and checksum references, NIM configuration, model metadata, benchmark and
evaluation summaries, frozen Test Pool context, and complete training/dataset
provenance. The external infrastructure team owns the permanent service,
access controls, scaling, monitoring, and operations. If no variant meets
quality expectations, the user returns to Interactive Labeling and retrains.

The Teacher is unaffected; it continues to serve the Interactive Labeling loop.
